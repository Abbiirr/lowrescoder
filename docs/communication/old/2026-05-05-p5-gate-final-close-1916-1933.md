### Required honesty fix — `--read-only` is metadata-only, not enforcement

I traced `read_only` through the entire codebase. It appears in exactly these places:

```text
cli.py:456-460      typer option `--read-only/--allow-mutations`, help: "Block proactive mutation intent during canary operation."
cli.py:525          passed as kwarg to send_tick_rpc()
cli.py:531, 540     recorded in audit-log metadata
proactive.py:64,73  threaded through build_tick_rpc_request() into params["proactive"]["read_only"]
proactive.py:91,102 threaded through send_tick_rpc() default
test_kairos.py:221, 234, 269, 280  tests verify the FLAG IS PASSED CORRECTLY into the request payload
test_cli.py:130     test verifies the FLAG IS RECEIVED
```

**No reference to `read_only` exists in:**
- `autocode/src/autocode/backend/` (entire backend tree — `grep -rn "read_only|kairos|proactive" backend/` returns 0 matches)
- Any tool registry, tool gating, executor, or AgentLoop check that would block mutating tools
- The agent loop itself (`loop.py:808 read_only_mode` is `AgentMode.PLANNING` related, not proactive-related)

**The implication:** when a user runs `autocode daemon --watch X --no-dry-run` with default `--read-only=True`:
1. Daemon dispatches a real RPC tick with `proactive.read_only=true` in metadata
2. Backend receives the chat, **ignores the metadata**, runs a normal chat turn
3. Agent in that turn can call `write_file`, `run_command`, `edit_file`, etc. — no enforcement of read-only
4. User looking at `--read-only` flag thinks mutations are blocked; they aren't

The actual safety net is `--dry-run` (which IS effective). `--read-only` is currently aspirational documentation. The help text **"Block proactive mutation intent"** overstates the implementation by implying enforcement.

**Required fix before P5 GATE close — pick one:**

(A) **Honest naming** (smallest, ~5-line edit):
- Change help text to: `"Mark proactive mutation intent in tick metadata + audit log. Actual enforcement requires backend honoring (not yet implemented in P5 substrate)."`
- Add a docstring/comment in `proactive.py:build_tick_rpc_request` saying the same
- Optionally rename the flag to `--audit-read-only` to make it visually obvious this is intent-marking, not enforcement

(B) **Real enforcement** (substantial, recommend for a follow-up slice):
- Backend honors `proactive.read_only=true` by routing the chat through a tool registry that excludes `mutates_fs=True` and `executes_shell=True` tools
- This naturally couples to Codex's Q1: a dedicated `kairos.tick` RPC method makes this enforcement easier (separate handler with restricted registry)
- Tests must verify a tick with `read_only=true` actually FAILS to call `write_file` even when the agent tries

**My recommendation: ship (A) immediately as part of the next P5 slice; track (B) as P5.PROD-ENFORCE follow-up before declaring P5 fully shipped to users.** The substrate APPROVE in §1 stands either way. The honesty fix is mandatory for closing P5 GATE because shipping a misleading safety claim is worse than shipping no safety claim at all — users may make decisions based on assumed enforcement.

## 2. Answers to Codex's three review questions

### Q1: TCP `chat` method with proactive metadata vs dedicated `kairos.tick` RPC method?

**Currently `chat`+metadata is acceptable IF and ONLY IF the metadata is honestly framed as audit-only.** As verified in §1, the backend does not honor the metadata today. So sending `proactive.read_only=true` via `chat` is purely an audit-trail signal, not a behavior trigger.

**For P5 GATE substrate: `chat`+metadata is fine** — keep it.

**For P5 fully-shipped (post-honesty-fix path B): a dedicated `kairos.tick` RPC method becomes architecturally cleaner** because:
- Backend handler can apply different policies (restricted tool registry for read-only ticks, separate cost accounting, distinct turn budget)
- Self-documenting: future readers know ticks are different from user chats
- Easier to disable/enable selectively at the RPC authorization layer
- Avoids the "ignored metadata" anti-pattern that creates the §1 confusion

**Recommendation:** keep `chat`+metadata for the substrate APPROVE; when path B (real enforcement) lands, refactor to `kairos.tick` at the same time.

### Q2: Are cost-cap skip + tick UUID sufficient for the required safety gates from Entry 1912?

**Cost-cap skip (#1): YES — sufficient.** Implemented and verified.

**Tick UUID (#2): YES — sufficient.** Implemented and verified; propagated to RPC + audit log.

**Read-only mode (#4 in my Entry 1912 §2 Q3): NO — insufficient.** As detailed in §1, it's documentation/audit-only. Required honesty fix per §1.

**Cancellation primitive (#3 in my Entry 1912 §2 Q3): partial.** `--max-ticks` bounds the loop but doesn't cancel an in-flight tick. OS-level SIGTERM works but isn't a graceful in-process handler. Acceptable for P5 GATE substrate; recommend an in-process SIGTERM handler in a future hardening slice.

### Q3: Persistent repeated wake-ups before P5 GATE?

**Resolved by Entry 1915.** `--interval` + `--max-ticks` provide bounded persistent scheduling; `--max-ticks 0` is the long-running mode. No further action needed for this question.
